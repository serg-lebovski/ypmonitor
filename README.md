# YPMonitor — мониторинг резервного копирования

Система из двух частей для контроля резервного копирования на множестве серверов клиентов:

- **Агент** — лёгкое приложение под Windows. Ставится на сервер, где уже кто-то делает бэкапы
  (любым способом). Агент **ничего не бэкапит сам** — он только наблюдает: смотрит папки с бэкапами
  и журнал событий Windows, и отправляет итоги на сервер.
- **Сервер** — центральная точка (Docker/Linux). Принимает данные от агентов, показывает дашборд
  по всем клиентам и серверам, ведёт страницу ошибок, шлёт оповещения и **отчёты в Telegram**.

Технологии: .NET 8, ASP.NET Core (Razor Pages), EF Core (SQLite или PostgreSQL), Docker Compose.
Агент — self-contained `.exe` (служба Windows). Сервер — набор контейнеров.

## Как это работает в целом

```
┌─────────────────────┐   POST /api/report (X-Api-Key)   ┌──────────────────────────────┐
│  Агент на сервере   │ ───────────────────────────────▶ │        Сервер YPMonitor        │
│  клиента (Windows)  │   каждые 60 с — heartbeat         │  (Docker: postgres+server+awg) │
│                     │   каждые 6 ч — полный отчёт       │                                │
│ • папки с бэкапами  │                                   │ • дашборд, страница ошибок     │
│ • журнал событий    │ ◀───── ответ: "нужен отчёт?" ──── │ • Telegram-бот (темы клиентов) │
└─────────────────────┘        (флаг ReportRequested)     └──────────────┬─────────────────┘
                                                                         │ SOCKS5
                                                          ┌──────────────▼─────────────────┐
                                                          │  Сайдкар AmneziaWG (обход DPI)  │
                                                          └──────────────┬─────────────────┘
                                                                         │ туннель
                                                                    Telegram API
```

- Соединение **строго одностороннее**: агент только отправляет отчёты (исходящее HTTP),
  сервер агенту команд не шлёт. Единственная «обратная связь» — булев флаг «прислать отчёт вне графика»,
  который агент сам вычитывает в ответе на heartbeat.
- Сервер сам оценивает состояние каждой папки (свежие бэкапы есть/нет по порогу в днях) и рассылает
  отчёты в Telegram — по одной теме на клиента, отдельным сообщением на каждый сервер.

## Агент (Windows)

Агент делает ровно **три вещи** (сознательно минимальный, версия 2.x):

1. **Подключение к серверу** — адрес сервера и API-ключ клиента.
2. **Наблюдение за папками бэкапов** — по каждой папке считает: число файлов, суммарный объём,
   имя и дату самого свежего файла (**любой формат** — zip, bak, dump, что угодно). Порог устаревания
   («нет новых файлов N дней → тревога») задаётся **на сервере**, не в агенте.
3. **Чтение журнала событий Windows** — ошибки (опционально предупреждения) из `System`/`Application`
   попадают в отчёт и на страницу ошибок сервера. Что игнорировать — настраивается на сервере.

Агент **не слушает порты, не принимает команд и сам ничего не архивирует**.

### Два режима из одного `Ypmon.Agent.exe`

- **Двойной клик** → окно настроек (WinForms, навигация слева). Пока окно открыто, агент уже шлёт отчёты.
- **Служба Windows** `YpmonAgent` → тот же exe в фоне без окна, читает тот же `config.json`.

Системный мьютекс гарантирует, что активен только один экземпляр (служба ИЛИ окно) — без дублирования.

### Разделы окна (слева направо)

| Раздел | Что настраивается |
| --- | --- |
| **Настройки подключения к серверу** | Адрес сервера и **API-ключ** (из веб-интерфейса: *Клиенты → сервер → «Данные для подключения агента»*). Кнопка проверки связи. |
| **Задания архивации** | Список наблюдаемых папок. По каждой: имя, путь (в т.ч. сетевой `\\сервер\папка`), учётная запись Windows для сетевого доступа. **«Сохранить задачу мониторинга»** явно фиксирует папку. |
| **Информация об отчётах** | Что и когда уходило на сервер: последний отчёт, статусы папок, найденные ошибки журнала. |
| **Настройка приложения** | Интервал отчёта (по умолчанию 6 ч), имя службы, автообновление, установка/удаление/запуск/остановка службы (через UAC). |
| **О приложении** | Версия и краткая справка. |

Настройки хранятся в `config.json` рядом с exe. Ключевые поля — в [`AgentConfig.cs`](src/Ypmon.Agent/AgentConfig.cs):
`ReportIntervalSeconds` (21600 = 6 ч), `HeartbeatIntervalSeconds` (60), `Folders[]`, `EventLog{}`.

## Сервер и веб-интерфейс

Веб-интерфейс: `http://<хост>:8080/`. При первом входе создаётся администратор.

- **Дашборд** — клиенты и их серверы, статус каждого: ✅ ок / ⚠️ предупреждение / ❌ ошибка / ⚫ офлайн.
  Клик по серверу → детали: наблюдаемые папки (число файлов, объём, дата свежего бэкапа), кнопка
  **«Запросить отчёт»** (ставит флаг, который агент подхватит на ближайшем heartbeat).
- **Клиенты** — клиенты (группы серверов) и серверы внутри них; добавление/**редактирование** клиента,
  выдача/перевыпуск API-ключей, персональный порог «нет бэкапов N дней».
- **Ошибки** — сводка ошибок Windows, присланных агентами.
- **Настройки** — сгруппированы в сворачиваемые секции:
  - 🔄 **Обновление сервера** (git-based, см. ниже);
  - 🤖 **Telegram-бот** — токен, ID группы, публичный адрес для ссылок, ежедневный отчёт, час по Омску,
    и кнопка **«📨 Разослать отчёт по клиентам сейчас»** (проверка в реальном времени);
  - 🚫 **Обход блокировки телеграмма** — конфиг AmneziaWG/WireGuard (см. ниже);
  - 🔔 **Оповещения и обслуживание** — порог офлайн, хранение истории, порог устаревания бэкапов,
    игнор-лист ошибок Windows, e-mail (SMTP);
  - ⬇️ **Установщик агента**, 🖥️ **Параметры сервера**, 👤 **Профиль**, 👥 **Пользователи**.

**Роли:** **Администратор** — полный доступ (включая настройки сервера и пользователей);
**Инженер** — просмотр, добавление и редактирование клиентов и серверов, без настроек сервера;
**Мониторинг** — только просмотр.

Оценка состояния папки — на сервере: если самый свежий файл старше порога (в днях), сервер помечает
папку проблемной. Если агент молчит дольше порога «офлайн» — сервер помечает сервер офлайн.

## Telegram-бот и ежедневные отчёты

Бот шлёт отчёты по архивации в **супергруппу с включёнными Темами (Topics)** — по одной теме на клиента.

**Как устроено:**

- При добавлении клиента (или по кнопке «Создать темы клиентов») бот вызывает `createForumTopic`
  и запоминает `TelegramTopicId` клиента.
- **Ежедневно в заданный час по Омску** (UTC+6, по умолчанию 10:00) `DailyReportScheduler` рассылает
  отчёт: в тему клиента — заголовок с датой и по одному сообщению на каждый его сервер
  (✅ «архивация успешна» / ❌ «ошибка архивации» + причина + ссылка на страницу сервера).
- Кнопка **«📨 Разослать отчёт по клиентам сейчас»** в настройках делает то же самое немедленно —
  для проверки в реальном времени.

**Настройка бота:**

1. Создайте бота у @BotFather, получите токен.
2. Создайте супергруппу, включите в ней **Темы (Topics)**, добавьте бота **администратором**
   (право управлять темами и писать).
3. В *Настройки → Telegram-бот* впишите токен и **ID группы** (для приватной супергруппы это
   `-100` + внутренний id, напр. `-1004479419901`). Кнопка **«Определить chat_id»** помогает его узнать
   (сначала напишите что-нибудь в группе).
4. Укажите **публичный адрес сервера** (для кликабельных ссылок в отчётах), включите ежедневный отчёт,
   сохраните → «Создать темы клиентов» → «Разослать отчёт сейчас» для проверки.

> Отчёты от агентов приходят раз в 6 часов, поэтому «свежесть» отчёта в Telegram — в пределах этого окна.
> Кнопка «Запросить отчёт» на странице сервера форсирует внеплановый отчёт от конкретного агента.

## Обход блокировки Telegram (AmneziaWG)

Там, где Telegram блокируется на уровне DPI (напр. в РФ), сервер не может напрямую достучаться до
Bot API. Решение — **сайдкар-контейнер с AmneziaWG** (обфусцированный WireGuard, userspace),
который поднимает туннель до незаблокированного VPN-сервера и отдаёт **SOCKS5** остальным контейнерам.
Бот ходит в Telegram через этот SOCKS5.

```
ypmon-server ──socks5://awg:1080──▶ ypmon-awg (amneziawg-go + microsocks) ──туннель──▶ VPN ──▶ Telegram
```

- Образ сайдкара: [`installers/awg-sidecar/`](installers/awg-sidecar) — собирает `amneziawg-go`
  и `amneziawg-tools` из исходников, плюс `microsocks`.
- Сервер пишет конфиг в общий том (`YPMON_AWG_CONFIG=/app/awg-out/awg0.conf`), сайдкар отслеживает
  его по md5 и переподнимает туннель при изменении.
- Включается переменной `YPMON_AWG_SOCKS=awg:1080` у сервера (уже прописано в `docker-compose.yml`).
- В unprivileged-LXC (Proxmox) wg-quick не может `sysctl src_valid_mark`, поэтому
  [`entrypoint.sh`](installers/awg-sidecar/entrypoint.sh) использует `Table = off` и правит маршруты
  вручную (endpoint — напрямую через реальный шлюз, дефолт — в туннель).

### Требование к хосту: устройство `/dev/net/tun`

Сайдкару нужен TUN. В обычном Docker-хосте он есть. В **unprivileged-LXC (Proxmox)** его надо пробросить
в конфиге контейнера `/etc/pve/lxc/<CTID>.conf`:

```
lxc.cgroup2.devices.allow: c 10:200 rwm
lxc.mount.entry: /dev/net/tun dev/net/tun none bind,create=file
```

затем `pct reboot <CTID>`. Настройка постоянна (переживает перезагрузки).

### Как заменить конфиг при смене VPN-сервера Amnezia

В *Настройки → 🚫 Обход блокировки телеграмма* есть подсказка «❓ Какой конфиг сюда вставлять»
и **поле для вставки конфига текстом** (предзаполнено текущим). При смене сервера Amnezia:

1. В приложении **AmneziaVPN**: нужный сервер → «Настройки подключения» → протокол **AmneziaWG**
   → экспорт/показ конфига.
2. Скопируйте весь текст (`[Interface] … [Peer]`) в поле (или загрузите `.conf` — файл имеет приоритет).
3. Галочка «Использовать…» → **«Сохранить и применить»** → **«Проверить»** (покажет внешний IP через
   туннель — должен отличаться от IP сервера).

Конфиг должен содержать `[Interface]` (`PrivateKey`, `Address`, параметры обфускации `Jc, S1, H1…`)
и `[Peer]` (`PublicKey`, `Endpoint` = адрес:порт незаблокированного сервера). Обычный WireGuard тоже
подойдёт, но его чаще режет DPI — надёжнее AmneziaWG.

> Обычный MTProto-прокси Telegram для бота не годится: он работает только с клиентским протоколом
> Telegram, а бот использует **HTTP Bot API** — для обхода блокировки боту нужен именно
> WireGuard/AmneziaWG.

## Развёртывание сервера (Docker)

`docker compose` поднимает **три контейнера**: `postgres`, `ypmon-server`, `ypmon-awg` (сайдкар).

```bash
# 1. Docker и git (Ubuntu/Debian)
sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2 git

# 2. Репозиторий
git clone https://github.com/serg-lebovski/ypmonitor.git
cd ypmonitor

# 3. .env (в git не попадает) — задать пароль БД
cp .env.example .env
nano .env            # POSTGRES_PASSWORD=...

# 4. Запуск
sudo docker compose up -d --build

# Логи / статус
sudo docker compose logs -f
sudo docker compose ps
```

`.env`:

```
YPMON_HTTP_PORT=8080
POSTGRES_PASSWORD=ваш_пароль
```

- БД `postgres` наружу не публикуется (доступна только серверу по внутренней сети compose).
  Данные — в томе `ypmon-pgdata`.
- Тома: `ypmon-data` (ключи DataProtection + sqlite — переживают пересборку), `ypmon-awg`
  (общий конфиг туннеля), `ypmon-updates` (сюда кладут `Ypmon.Agent.exe` для автообновления агентов).
- Порты: `8080` — веб-интерфейс, `8081` — приём отчётов от агентов.

> Секреты (пароль БД, токен бота, приватные ключи WireGuard) хранятся **только в `.env` и БД**,
> в git не коммитятся.

### Установщик агента

Готовый `YpmonAgent-Setup.exe` кладётся в том `ypmon-updates` (`/app/agent-updates`) и скачивается
со страницы *Настройки → Установщик агента* (`/agent-installer`). Он ставит агента в
`C:\Program Files\ypmonitor` и регистрирует службу; мастер спрашивает адрес сервера, API-ключ и
учётную запись службы.

## Обновление сервера и агентов

### Сервер (git + кнопка)

Самообновление идёт через git-репозиторий и воркер `ypmon-updater` (systemd на хосте, канал через том
`./.update`). В *Настройки → 🔄 Обновление сервера*: **«Проверить обновления»** → при наличии новых
коммитов **«Установить обновление»** (сервер делает `git pull`, пересобирается и перезапускается ≈1–3 мин).

Вручную: `git pull && sudo docker compose up -d --build`.

> На Proxmox под root по чужому (admin_yp) репозиторию `git pull` может упасть с «dubious ownership» —
> один раз выполнить `git config --global --add safe.directory <путь-к-репо>`.

### Агенты (с сервера, автоматически)

1. Поднимите `<Version>` в `Ypmon.Agent.csproj`, соберите, положите новый `Ypmon.Agent.exe`
   в `agent-updates` на сервере.
2. Агент с включённым автообновлением раз в день сверяет версию (`GET /api/agent/version` со своим
   `X-Api-Key`) и при наличии новой — скачивает и ставит с перезапуском службы.
3. Вручную — из окна агента: *Настройка приложения → «Проверить обновления сейчас»*.

Обновление всегда инициирует **сам агент** (скачивает по своему запросу) — сервер входящих соединений
к агенту не открывает. Тихая установка под службой не требует UAC (наследует токен службы).

## Модель безопасности

- **Агент — только исходящий.** Не слушает портов, не исполняет команд сервера. Единственный сигнал
  от сервера — булев флаг «прислать отчёт», который агент сам вычитывает.
- **API-ключ на каждый сервер**, перевыпуск ключа, PBKDF2-хеширование паролей пользователей.
- **Секреты не в git**: пароль БД — в `.env`, токен бота и ключи WireGuard — в БД. В репозитории их нет.
- **БД не опубликована наружу** — только внутренняя сеть compose.
- **DataProtection-ключи** сохраняются в томе `ypmon-data` — сессии/antiforgery переживают пересборку.
- **Сайдкару AmneziaWG** выдан только `NET_ADMIN` и `/dev/net/tun`; наружу он не публикует портов,
  SOCKS5 доступен лишь внутри compose-сети.

## Структура репозитория

```
ypmonitor/
├─ docker-compose.yml            — postgres + ypmon-server + awg (сайдкар)
├─ Dockerfile                    — образ сервера
├─ .env / .env.example           — секреты (в git только пример)
├─ src/
│  ├─ Ypmon.Shared/              — общие DTO/контракты (AgentReportDto, статусы)
│  ├─ Ypmon.Server/              — ASP.NET Core: Razor Pages (UI) + /api/report + сервисы
│  │  └─ Services/               — TelegramService, TelegramReportService, DailyReportScheduler,
│  │                              WireGuardProxyService, AlertService, ServerUpdateService …
│  └─ Ypmon.Agent/               — агент Windows (наблюдение за папками + журнал событий, WinForms)
├─ installers/
│  └─ awg-sidecar/               — Dockerfile + entrypoint.sh сайдкара AmneziaWG
├─ build/                        — скрипты сборки (build-all.ps1)
└─ deploy/, scripts/             — вспомогательные скрипты установки
```

Сборка (нужен .NET 8 SDK):

```powershell
pwsh build/build-all.ps1                       # всё
pwsh build/build-all.ps1 -Target agent-win     # только агент
```

## Частые вопросы и диагностика

**Бот пишет «Telegram выключен» / не шлёт отчёты.** Проверьте, что включён Telegram и задан токен + ID
группы, что бот — админ группы с включёнными Темами. Нажмите «Разослать отчёт сейчас» и смотрите текст
результата.

**«Не удалось получить внешний IP через WireGuard».** Туннель не поднялся: проверьте конфиг (кнопка
«Проверить»), наличие `/dev/net/tun` на хосте, логи сайдкара `docker compose logs -f awg`.

**Контейнер `awg` показывает `unhealthy`.** Healthcheck проверяет интерфейс `awg0` и порт `:1080`.
Если туннель не поднялся — см. предыдущий пункт; сразу после старта дайте `start_period` (30 с).

**Отчёт в Telegram «отстаёт».** Полные отчёты от агентов — раз в 6 ч. Форсировать: кнопка «Запросить
отчёт» на странице сервера (агент пришлёт на ближайшем heartbeat, ≤60 с).

**Сервер не обновляется по кнопке.** См. «dubious ownership» выше — на хосте выполнить
`git config --global --add safe.directory <путь>`.

**Агент не обновляется / просит UAC.** Автообновление под службой UAC не требует. Убедитесь, что
служба запущена под учёткой с правами на `C:\Program Files\ypmonitor`.

**Не устанавливается служба агента / «OpenService FAILED 1060».** 1060 означает, что службы нет —
то есть упал именно `sc create`, а не запуск. Агент теперь останавливается на этом шаге и показывает
настоящую причину (расшифровку кода `sc.exe`). Частые причины:

- **имя службы с пробелом или спецсимволом** — `sc` такое имя не принимает (проверка теперь до установки);
- **не подтверждён UAC** либо установку блокирует антивирус/групповая политика;
- **1069** — неверный пароль учётной записи или у неё нет права «Вход в качестве службы»
  (`secpol.msc` → Локальные политики → Назначение прав пользователя);
- **1072** — служба помечена на удаление: закройте `services.msc` и повторите;
- **пароль с кавычкой `"`** — `sc.exe` его не примет (агент предупредит заранее).

Запасной путь: в агенте (*Настройка приложения → Служба Windows*) под кнопками есть поле с готовой
командой установки — скопируйте её и выполните в командной строке **от имени администратора**.

---

Протокол вкратце: агент шлёт `POST /api/report` с `X-Api-Key`; сервер только подтверждает приём и,
при необходимости, возвращает флаг «нужен внеплановый отчёт». Никаких входящих соединений к агенту.
